### 2.2 日志格式

`train.py` 日志格式（get_logger）：`%(asctime)s | %(levelname)s | %(name)s | %(message)s`，datefmt=`%H:%M:%S`。
主进程写 stdout + `output_dir/train.log`（append）。

示例（阶段 4 检查正则）：
```
14:32:05 | INFO | train | [60/120] loss=1.2345 lr_core=1.00e-04 lr_vlm=1.00e-04 (1.02s/it) DATA_PCT=12% USED_CPU=1.23e+00 GB USED_GPU=5.67e+00 GB
14:32:05 | INFO | train | DECODE timing: 8.5 ms/sample | 145 fps/frame | decode 35% of worker wall (samples=960, frames=72000)
```
检查项：行首时间戳、step 计数（`/120`）、`loss/lr_core/lr_vlm`、`effective_batch=32`、
`DATA_PCT`（数据预处理时间占比）、`USED_CPU/USED_GPU`、训练结束的解码计时聚合行。

### 2.5 数据转换与 handler 是否符合预期

`scripts/check_data.py` 端到端覆盖：

| 检查项 | 预期 |
| --- | --- |
| 主表 `observation.state`/`action` | 形状 [N,20]、float32、行数一致 |
| `meta/stats.json` | state/action 20 维统计（min/max/mean/std/count/q01..q99），count=总行数 |
| `meta/info.json` | features state/action shape=[20] |
| `meta/episodes` | `stats/` 前缀列已剔除 |
| 视频 | 相机目录存在、symlink 目标存在（symlink 指回 src） |
| handler 样本 | domain_id=6、image_input[3,3,224,224]、proprio[20]、action[30,20]、指令非空、image_mask[3] |
| gripper 取值 | 反转后 ∈[0,1]（1-g 语义） |
| **训练集过滤** | `meta.json.episodes` = splits `train` 列表（1080 个），handler datalist 长度一致、索引合法 |

> **注意（训练必须用划分的训练集 episode 索引）**：整条链路要求训练只接触划分文件的
> 训练集索引，禁止把全部 1200 个 episode（含 val 120 个）喂给训练。链路与校验点如下：
>
> 1. `prepare_data.sh` 读 splits `train` 列表写入 `meta.json.episodes`（缺失时打印 warn 并退化为全部
>    episode，此时训练集过滤失效，必须在阶段 2 判定 FAIL）。
> 2. `train.sh`/`train.py` 经 `InfiniteDataReader` → `LeRobotV3RoboDojoHandler`，
>    handler `_load_episodes` 按 `meta['episodes']` allowed 集合过滤（lerobot_v3_robodojo.py）。
> 3. 阶段 2 `check_data.py` 断言 `handler datalist 长度 == len(meta.episodes) == 1080` 且索引在
>    `[0, 1200)`；阶段 4/5/6 冒烟均以该 `meta.json` 为训练元数据，训练数据 = 训练集 1080 个 episode。

此外阶段 3 跑 pytest（handler/dataset_reader/make_goai_20d），用 `XVLA_DATA_ROOT` 指到服务器数据；
`test_handler.py` 的 `test_20d_matches_reference_conversion` 需要 16 维源数据（`ROOT_16=/data/data/lerobot_v30_ee`），
服务器有完整 16d 数据故正常执行。

### 2.6 视频解码 / 数据预处理耗时量化（新）

目标：回答"每个训练 step 里数据预处理占多少，其中视频解码花多少"。

测量链路（train.py + xvla_datasets/timing.py，仅 `--timing_dir` 开启时生效）：
1. **DATA_PCT**（主进程）：每 log 间隔累计 `next(train_iter)` 墙钟（含 worker 解码 + image_aug + IPC），
   占该间隔总墙钟比例 → `DATA_PCT=xx%`。
2. **decode 指标**（DataLoader worker 侧）：`_decode_episode_video` 累计解码墙钟与帧数，每 64 样本
   flush 到 `<timing_dir>/<rank>/decode_<pid>.jsonl`；训练结束主进程聚合 → `summary.json`：
   - `decode_ms_per_sample`：每样本平摊解码毫秒
   - `decode_fps`：解码帧率（AV1 640×480）
   - `decode_pct_of_worker_wall`：解码占 worker 处理时间的比例
3. 全量外推：完整训练期每 episode 整段解码一次 → 总解码成本 ≈ 1200 eps × 平均帧/episode × decode_fps⁻¹，
   与 200k 步训练总时长对比，判断是否瓶颈（todo.md 方案 A/B 留档）。

冒烟期只有 ~960 样本（≈2 个 episode 被访问），DATA_PCT 会偏低——这本身说明短训数据加载不是瓶颈；
真正的解码吞吐由 `decode_fps` 量化，可外推到长训。
